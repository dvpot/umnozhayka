2. Последовательно выполни `npx tgcloud fetch`, `npx tgcloud status`, `npx tgcloud diff`. Подтверди app ID `8854507045`, фактическую исходную revision и отсутствие неожиданных изменений. От revision 9 ожидаются новая таблица `table_progress`, изменения `tgcloud/schema.js`, новые `tgcloud/lib/table-progress.js` и `tgcloud/endpoints/tableProgress.js`, обновления `dist/app.js`, `dist/engine.js`, `dist/index.html` и `dist/styles.css`. 3. Проверь `npx tgcloud migrate --local --dry-run`. При ожидаемом добавлении одной таблицы опубликуй только модули: `npx tgcloud push tgcloud/schema.js tgcloud/lib/table-progress.js tgcloud/endpoints/tableProgress.js`. Выполни `npx tgcloud migrate --dry-run`, проверь ту же безопасную миграцию и примени `npx tgcloud migrate --safe`. Повторный dry run должен показать отсутствие ожидающих изменений. Если появляется иной план или предупреждение, установи причину перед изменением БД.
4. Перед статикой повтори `fetch/status/diff`. Опубликуй сборку отдельно: `npx tgcloud push dist`. Не используй `--force` и не запрашивай секреты. После выкладки повтори `fetch/status/diff`, проверь актуальную revision, HTTP 200 и соответствие четырёх статических файлов сборке. В реальном Telegram проверь чтение/сохранение с подписанным контекстом, второй клиент того же аккаунта и удаление. Изоляцию второго аккаунта проверь, если он доступен. Фактические и имитированные проверки запиши отдельно.
5. Подтверждённый результат — SHA, шаги миграции, старая и итоговая revision, app ID, diff, HTTP и результаты Telegram — зафиксируй в `docs/TELEGRAM_DEPLOY.md` отдельным PR с CI. После слияния синхронизируй VM.

Если CLI сообщил ошибку записи snapshot после загрузки, повторный push вслепую не нужен. Сначала подтвердить состояние через fetch/status/diff.
