# Codex на Ubuntu VM — выпустить проверенный текущий main в Telegram Serverless

Рабочий каталог: `/home/dvpot/projects/github/umnozhayka`. Источник истины: `dvpot/umnozhayka`, ветка `main`. Выпускай только актуальный `main` после слияния PR с узкой раскладкой и встроенной озвучкой. Перед работой сверь текущий SHA с GitHub; локальный SHA из предыдущего отчёта не считать целевым, если `main` продвинулся.

Прочитай `AGENTS.md`, `README.md`, `docs/PLAN.md`, `docs/TELEGRAM_DEPLOY.md`, `docs/CODEX_CHECK_QA_TASK.md` и этот файл. Начни с `git status -sb`, `git fetch origin` и проверь текущий `main`. Сохрани любые локальные изменения. Синхронизируй чистый `main` только fast-forward и запиши SHA.

1. Сверь свой отчёт предыдущего preflight с текущим SHA. Если его нет или он относится к другому SHA, повтори проверки: `npm ci && npm run check`, `node --check app/app.js`, `git diff --check`. Проверь в браузере ширины 280, 320, 390, 768 и 1024 px без горизонтальной прокрутки. Карточка должна быть компактной и геометрически одинаковой по структуре во всех режимах; проверь уменьшенный интервал между строками и под ответом. В окнах 400×612, 320×480 и 768×720 CSS px клавиатура проверки, строка статистики и кнопки должны помещаться без вертикальной прокрутки. Сверь одинаковый шрифт ответа в «Тренировке» и «Проверке» и стрелки по центру карточки. Проверь свайп, начинающийся поверх ответа, вариантов и стрелок: он меняет задание и не активирует попавшую под конец жеста кнопку; обычные нажатия на эти элементы работают. Сохраняй регрессионные проверки: ответ тренировки отключается после показа; порядок вариантов не меняется после неверного выбора и восстановления; стрелка назад отключена до правильного ответа; клавиатура появляется только в «Проверке»; неверный ввод нейтрален при редактировании и окрашивается после отправки; после смены режима/таблицы начинаются новый проход и счёт; счётчик неверных попыток сохраняется после исправления; проверка сброса и итогового экрана. Следуй также сценарию `docs/CODEX_CHECK_QA_TASK.md`.
2. Выполни по порядку `npx tgcloud fetch`, `npx tgcloud status`, `npx tgcloud diff`. Сверь app ID `8854507045` с настройками `@umnozhayka_tgbot`, ревизию и список модулей. Ожидаются только изменения статики Mini App, включая `recorded-speech.js`, `assets/voice-cues.js` и `assets/voice-ru.mp3`. Разберись с любыми неожиданными изменениями, сохрани чужие серверные данные и подготовь чистый ожидаемый diff. Не используй `--force`, не читай и не выводи секреты.
3. Когда тесты, браузерная приёмка, app ID и diff подтверждены, выполни `npm run deploy`. При конфликте сначала снова получи свежий снимок и безопасно устрани причину. Если CLI завершится ошибкой записи snapshot после загрузки, не запускай push повторно вслепую.
4. После загрузки снова выполни `npx tgcloud fetch`, `npx tgcloud status` и `npx tgcloud diff`. Подтверди новую фактическую revision, нужные модули, актуальную статику и отсутствие непредвиденных удалений. Проверь HTTP `200` приложения и открытие обновлённого интерфейса с чистой загрузкой. Сверь HTTP `200` и SHA-256 `assets/voice-ru.mp3` с локальным файлом. В Chromium без Web Speech API проверь запуск встроенного аудио после переключения звука и перехода к следующему примеру. На Android в Telegram проверь слышимые фразы включения и выключения, следующий пример и ответ, а в Telegram Desktop — целиком видимую кнопку «Проверить». Запиши клиент, ОС, фактический viewport и результаты. Если реальный клиент недоступен, отметь его проверку как невыполненную.
5. Зафиксируй фактический результат публикации в `docs/TELEGRAM_DEPLOY.md` отдельным PR с CI, затем синхронизируй VM с новым `main`. В отчёте в чат укажи исходный и итоговый SHA, тесты, браузер и ширины, app ID, старую и новую revision, точный итог `diff`, HTTP-проверку, доступную проверку Telegram и ссылку на PR. Разделяй локальную QA и проверку живого Telegram.

Не объявляй публикацию успешной по одному коду выхода `npm run deploy`: подтверди состояние сервера последующим `fetch/status/diff`.
